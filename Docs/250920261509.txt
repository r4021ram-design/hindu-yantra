# PHASE 1 — SVG ASSET REGISTRY

## Goal

Create a single reliable source of truth for Yantra SVG assets.

Current application contains multiple SVG folders and several root-level duplicate/legacy SVG files.

Do NOT delete anything immediately.

First classify assets.

Create a canonical registry such as:

`src/lib/yantras/yantra-assets.ts`

or another appropriate architecture if the existing project has a better location.

The registry should provide:

```ts
type YantraAsset = {
  id: string;
  svgPath: string;
  category: string;
  aliases?: string[];
  fallbackPaths?: string[];
};
```

Use the existing project taxonomy/data rather than creating duplicate metadata.

---

## Registry requirements

The application should be able to resolve:

```ts
getYantraAsset(yantraId)
```

and receive the canonical SVG asset.

Avoid scattered logic such as:

```ts
/yantras/${id}.svg
/yantras/category/${id}.svg
/yantras/${id.replace(...)}.svg
...
```

inside UI components.

Move asset resolution into one centralized layer.

---

## Canonical asset rules

For every Yantra:

1. Identify the actual verified SVG.
2. Assign one canonical path.
3. Preserve aliases only when necessary for backward compatibility.
4. Do not change SVG content.
5. Do not regenerate SVGs.
6. Do not alter SVG geometry.

---

## Duplicate assets

Find duplicate or suspicious files such as:

* `Shriyantra.svg`
* `SriYantra.svg`
* `sri_yantra.svg`
* other root-level duplicates
* category-level duplicates

Do NOT delete them automatically.

First determine whether they are referenced.

If safe:

* migrate references to canonical assets
* remove obsolete duplicates only when proven unused

If deletion could be risky:

* keep them
* mark them as legacy
* ensure the application no longer depends on them
